# macos-code-signer: macOS code-signing CLI

Rust CLI that signs Mach-O binaries, `.app` bundles, `.pkg` installers and `.dmg` disk images with a Developer ID certificate whose private key never leaves the signing service. It computes the CodeDirectory/CMS digest locally with the `apple-codesign` crate, sends only that digest to `macos-signing-service` over HTTPS with an OIDC bearer token, and embeds the returned signature locally.

See `README.md` for usage and the service API.

## Design notes

- **CLI parsing** (`src/main.rs`): `clap`-based. Fetches the certificate for `--cert-id` up front (`SigningServiceClient::get_certificate`), builds a `RemoteKeyInfoSigner`, checks the cert type against the input, then delegates to `apple_codesign::UnifiedSigner`.
- **HTTP client** (`src/client.rs`): `SigningServiceClient` speaks the service's JSON:API-shaped HTTP surface. Requires HTTPS unless the target is loopback (for local testing). Parses the base URL once and rejects credentials, query or fragment in it. Sends the certificate ID as one percent-encoded path segment, rejecting empty, `.`, `..`, `/`, `\` and control characters without any request. A single path decode yields the ID verbatim; servers or proxies that decode more than once are not defended. Disables redirects: reqwest keeps the `Authorization` header on a same-host redirect, which could leak the OIDC token to plaintext HTTP. Times out after 30 seconds. `sign_digest` reports a `409` as a clear "certificate was rotated since fetched, re-fetch and retry" error.
- **Remote signer** (`src/signer.rs`): `RemoteKeyInfoSigner` implements `x509_certificate`'s `KeyInfoSigner`/`Sign`/`Signer` traits so `apple_codesign::SigningSettings` can use it as a drop-in signing key. Hashes with SHA-256 and signs PKCS#1 v1.5, so only RSA certificates are supported. No private key material is held locally: `private_key_data` always returns `None`.
- **Signing settings** (`src/settings.rs`): `build()` constructs `apple_codesign::SigningSettings` and resolves the issuing chain from the leaf with `chain_apple_certificates()`. A self-signed leaf (throwaway test certificates) is signed with no chain. Any other unresolvable leaf is a provisioning error and fails.

## Layout

- `src/main.rs`: CLI entrypoint, argument parsing, the `sign` subcommand.
- `src/client.rs`: `SigningServiceClient`, the HTTP client for the signing service.
- `src/signer.rs`: `RemoteKeyInfoSigner`, the remote-backed `KeyInfoSigner`.
- `src/settings.rs`: `SigningSettings` construction (chain resolution, flags, entitlements, timestamp).
- `scripts/gen-test-artifacts/`: shell scripts that build Mach-O, `.app`, `.dmg` and `.pkg` artifacts. The Mach-O and `.app` executable are ad-hoc signed by the linker on arm64 unless `--unsigned` is passed. The others are unsigned. The E2E tests build their inputs with them. Also used for manual testing against a deployed service.
- `scripts/install-rcodesign.sh`: installs a pinned, checksum-verified `rcodesign` build (macOS universal or Linux x86_64, picked from `uname -s`) into a given directory. Used by `scripts/sign-legacy.sh` (macOS signing job) and `scripts/notarize.sh` (Linux notarization job).
- `scripts/sign-legacy.sh`: signs release binaries in place with the bootstrap Developer ID Application certificate (a `.p12` plus `rcodesign`). GitHub Actions only, see "Releases".
- `scripts/notarize.sh`: zips signed release binaries and submits them to Apple's notary service with `rcodesign`, waiting for the result. See "Releases".
- `scripts/check-release-binaries.sh`: fails unless a target directory holds exactly the three release binaries (aarch64, x86_64, universal) as regular files with the expected architectures. Run by the signing jobs before signing.
- `scripts/package.sh`: builds the release tarballs (binary, `README.md`, `LICENSE`, `NOTICE` and `COPYING`, checked after packaging; `--latest` mode needs no `tar`) and `SHA256SUMS` for a given version (build mode), or copies already-built tarballs to fixed, unversioned names with a matching `SHA256SUMS` (`--latest` mode, see "Releases"). Used identically by `.github/workflows/release.yml`'s and `.gitlab-ci.yml`'s `package` jobs, so both releases are packaged the same way; `--latest` mode is also used by the GitLab `release-s3` job. Needs `tar` and a sha256 tool (`sha256sum` or `shasum`); neither mode needs macOS, even though the binaries it packages are macOS-only.
- `COPYING`, `COPYING.aarch64-apple-darwin`, `COPYING.x86_64-apple-darwin`: third-party license notices, one per release target from that target's dependency set, plus the union for the universal binary (`COPYING`). `scripts/package.sh` ships the matching one as `COPYING` in each tarball. Generated, never edited by hand: run `scripts/gen-copying.sh` after any `Cargo.lock` change; it regenerates all three (`--check` fails if any is stale). `about.toml` is the single config; the script passes `--target` per file. It renders `about.hbs` with a pinned, checksum-verified cargo-about (`scripts/install-cargo-about.sh`, macOS arm64 or Linux x86_64). `about.toml` sets the darwin targets, the accepted licenses in priority order (MIT first in OR choices) and checksum-pinned clarifications for license files cargo-about misses or misreads: ring's extra notices, liblzma-sys's bundled xz 0BSD, curve25519-dalek, chrono, libm, yasna and xml-rs. The script then appends the Rust runtime notices (std and compiler-builtins, including the LLVM exception), fetched from the pinned toolchain's tag and checksum-verified,. pear, pear_codegen and asn1-rs-impl only get the generic SPDX template text, flagged in `about.hbs`. The root crate is skipped in `about.hbs`, so a version bump does not make `COPYING` stale. Needs network access. Limitations: crates are listed with cargo-about's `crate.source` (the git rev for git and patched crates, the registry for crates.io ones, where name and version pin the archive). The Rust runtime notices are the repository's root `COPYRIGHT` and license files plus compiler-builtins' `LICENSE.txt`: the library-specific `COPYRIGHT-library.html` is generated at release time, not in the repository at the tag, so it can't be fetched by checksum from there. asn1-rs-impl's license file is at its repository root, which cargo-about's git clarification can't reach.
- `scripts/check-release-tag.sh`: fails unless a `vX.Y.Z` tag matches `Cargo.toml`'s version. Used by both CI systems before a release build runs.
- `scripts/cargo-version.sh`: prints `Cargo.toml`'s package version. Shared by `check-release-tag.sh` and both release workflows, so the version is only parsed in one place.
- `action.yml`: a composite GitHub Action that downloads the released binary for the runner's architecture, checks it against `SHA256SUMS`, verifies it like `verify-macos` does (signature, Datadog's Team ID `JKFCB4CN7C`, hardened runtime, online notarization check), and adds it to `PATH`.
- `scripts/sign.sh`, `scripts/verify-signature.sh`, `scripts/install-bootstrap-signer.sh`: signing through the signing service with the bootstrap release, see "Signing service". `tests/staging/` tests the sign and verify scripts with `unittest`, throwaway certificates, a local HTTPS mock and a stub signer: `python3 -m unittest discover -s tests/staging` (macOS, run by `test-macos`).
- `tests/e2e.rs`: end-to-end tests that run the built binary against a mock service.
- `tests/common/`: E2E helpers. `mock_service.rs` is a `wiremock` mock of the service API that signs with the E2E fixture key. `artifacts.rs` builds inputs with `scripts/gen-test-artifacts/` (macOS only).
- `tests/fixtures/`: throwaway self-signed key pairs. `test-*.pem` for unit tests, `e2e-developer-id-*.pem` (Developer ID-style extensions) for E2E tests. See `tests/fixtures/README.md`.

## Dependencies

`apple-codesign` and `apple-xar` are patched in `Cargo.toml` to an unreleased upstream git rev, because the crates.io release of `apple-codesign` depends on an older `x509-certificate` than this crate uses. Remove the patch once upstream publishes a release on `x509-certificate` 0.25.

## Releases

Both pipelines package on every trusted ref (`main` and `v*` tags), but only publish on a `v*` tag that matches `Cargo.toml`'s version:

- The version string is the tag's version (without the leading `v`) on a tag, or `<Cargo.toml version>-<short commit SHA>` on `main`.
- GitHub Actions (`.github/workflows/release.yml`) triggers on push to `main` and on `v*` tags. `build` (macOS, no environment or secrets) builds the binaries and uploads them unsigned. `sign` (macOS, `protected-main-env`, fresh VM with a sparse checkout of the signing scripts only, no toolchain) checks, signs and verifies them, then uploads them as an artifact. `notarize` (Linux, `protected-main-env`) submits them to Apple and waits. `verify-macos` (macOS) checks the signature, Team ID, hardened runtime and notarization. `package` (Linux) downloads the verified binaries, packages with `scripts/package.sh` and uploads the workflow artifact. `check-tag` always runs, but its version check only runs on a tag; a failed check blocks `build` and `package`. `check-copying` (Linux) runs `scripts/gen-copying.sh --check` and blocks `package` if `COPYING` is stale. `release` only runs on a tag, in the `protected-main-env` environment, so its ref restrictions and any configured approval rules apply.
- GitLab CI's `build-macos` builds the binaries and uploads them unsigned as an artifact, with no `id_tokens` or secrets. `sign-macos` (trusted refs only: `main` or a `v*` tag) checks, signs and verifies them through the production signing service in a separate job: fresh clone, no cache, no Rust toolchain, only the signing scripts run. `notarize` (Linux, trusted refs only) submits them to Apple and waits. `verify-macos` (trusted refs only) checks the signature, Team ID, hardened runtime and notarization. `package` (Linux) packages the binaries with `scripts/package.sh` (binary, `README.md`, `LICENSE`, `NOTICE`, `COPYING`) on `main` and on `v*` tags (`dist/` is a job artifact either way). `release-s3` only runs on `v*` tags.

**Signing and notarization:**

- GitHub Actions signs with a pinned, checksum-verified `rcodesign` and the `[GH]` Developer ID Application certificate stored as a legacy `.p12` in GitHub secrets (`protected-main-env`), with `scripts/sign-legacy.sh`.
- GitLab signs through the production signing service (`https://webhooks.build.datadoghq.com`) with the `[I]` Developer ID Application certificate (`prod-i-application-certificate`), as the `trusted-jobs` CI Identity, using the pinned v0.2.0 release: see "Signing service". No certificate or private key is read by the job.
- Both sign with hardened runtime and the `com.datadoghq.macos-code-signer` identifier.
- Notarization (`scripts/notarize.sh`) submits a zip of the signed binaries to Apple's notary service with `rcodesign notary-submit --api-key-file ... --wait`, using an App Store Connect API key from GitHub secrets or Vault. Bare Mach-O binaries can't be stapled, so the notarization ticket is only ever checked online, never attached to the binary.
- `verify-macos` runs `codesign --verify --strict --verbose=2`, checks `TeamIdentifier` and the `runtime` flag in `codesign -dvvv`, and checks the notarization ticket with `codesign --verify --check-notarization --test-requirement="=notarized"`. `--check-notarization` forces an online lookup: a bare binary can't be stapled, and a fresh runner has no cached ticket.
- On GitLab, `notarize` reads the App Store Connect key from `kv/ci/datadog/macos-code-signer/trusted-jobs/apple-connect-api-key` (field `json`) via a pinned `ci-identities-ci-job-client` and an `id_tokens` block requesting a `ci-identities` audience token, the same mechanism `release-s3` uses for AWS. It's the only GitLab job that reads a Vault secret.

On GitLab, `build-macos` and `package` both declare `needs: check-release-tag` (`optional: true`, since that job only exists on a `v*` tag). If the tag doesn't match `Cargo.toml`'s version, `check-release-tag` fails and blocks both: a mismatched tag never even starts the macOS build, so signing and packaging never run. `release-s3` uses `dependencies: [package]` instead of `needs`, so it's gated by stage order rather than its own need: it waits for every earlier stage (lint, including `check-release-tag`, then test, build, sign, notarize, verify and package) to finish before it can start. The `optional: true` need is a no-op on branch and MR pipelines, where `check-release-tag` doesn't exist.

**Publishing:**

- GitHub Releases are immutable once published, so `release` creates a draft with `gh release create --draft --verify-tag --generate-notes` and all the release files, then publishes it with `gh release edit --draft=false`. Nothing is ever uploaded to an already-published release.
- `release-s3` uploads to `s3://${RELEASE_S3_BUCKET}/macos-code-signer/<ver>/` (the versioned files, as packaged) and to `.../latest/` (the same files, copied and re-hashed under fixed, unversioned names with `scripts/package.sh --latest`, so `latest/` only ever holds the current release). It authenticates as the `trusted-jobs` CI Identity: an `id_tokens` block requests a `ci-identities` audience token, a pinned `ci-identities-ci-job-client` build exchanges it for AWS credentials (`assume-role --account-id 486234852809`) written to `AWS_SHARED_CREDENTIALS_FILE`, and that identity's IAM policy only allows `s3:PutObject`/`s3:GetObject` under `macos-code-signer/*` and `s3:ListBucket` with that prefix. There is no delete or ACL call anywhere in the job.

## Signing service

The binaries are signed with this tool itself, through macos-signing-service, using the pinned v0.2.0 release:

- Staging: on branches other than `main`, on both CI systems, through the staging deployment and a self-signed test certificate per CI system. Nothing packages or publishes the result: it's a 1-day artifact.
- Production: on GitLab `main` and `v*` tags, `sign-macos` signs through the production deployment with `prod-i-application-certificate`, and `MACOS_SIGNING_ENVIRONMENT: production`. Its output goes on to `notarize`, `verify-macos` and `package`. GitHub `main` and `v*` tags keep the `.p12` signing in "Releases".

Per CI system:

- GitHub: `.github/workflows/build.yml` (push to any branch but `main`; never tags). `build`, then `staging-sign`, which installs the v0.2.0 release with `action.yml`, gets a GitHub OIDC token for `macos-signing-service` from the runner's ID token endpoint with `curl` and `jq` (masked, set as a step output) and only passes it to the signing step. Job env values in the workflow: `MACOS_SIGNING_ENVIRONMENT` (`staging`), `MACOS_SIGNING_SERVICE_URL`, `MACOS_SIGNING_CERT_ID`, `MACOS_SIGNING_CERT_AUTHORITY` (the leaf common name).
- GitLab: `sign-macos` and `sign-macos-staging` extend the hidden `.sign-macos-service` job, which holds the stage, runner, `ci-identities` `id_tokens`, pinned client and bootstrap versions, and the script. They only differ by rules, environment variables and artifact expiry. Both write the signed binaries back to `target/` in the release layout. `sign-macos-staging` runs after `build-macos`, never on tags or the default branch, otherwise with `build-macos`'s rules. `scripts/install-bootstrap-signer.sh` installs the v0.2.0 universal release from binaries.ddbuild.io against a pinned SHA-256, then checks its signature, Team ID, hardened runtime and notarization. The token comes from `ci-identities-ci-job-client get-token --audience macos-signing-service`, requested last. The same four values are job variables in `.gitlab-ci.yml`, per job (`MACOS_SIGNING_CERT_AUTHORITY` only for staging).
- `sign.sh` requires an `https://` base URL without credentials, query, fragment or dot segments, and a certificate ID made of unreserved characters. A preflight GET of the certificate sends the token as a header read from stdin, follows no redirects and reports only the HTTP status. Signing uses the CLI's default RFC 3161 timestamp server.
- `verify-signature.sh` takes `MACOS_SIGNING_ENVIRONMENT` (`staging` or `production`, anything else fails) and checks each architecture, including both universal slices: signature, identifier, hardened runtime, leaf common name (`MACOS_SIGNING_CERT_AUTHORITY`, not the key, so rotations don't break it: required for `staging`, checked when set for `production`), then the environment's identity checks, then a secure timestamp. `staging`: a Team ID other than `JKFCB4CN7C`, no notarization or Gatekeeper check since the certificate is self-signed. `production`: Team ID `JKFCB4CN7C`, and Apple's Developer ID requirement (Apple anchor, Developer ID intermediate and leaf, leaf OU `JKFCB4CN7C`) via `codesign --verify --test-requirement`, so a self-signed certificate with a spoofed Team ID fails. Notarization is left to `verify-macos`.
- Boundary: on a branch, its author controls the workflow and scripts and can use the token. The service must only let these identities reach their own staging test certificate. The production service must only let the `trusted-jobs` identity, which the pipeline only uses on `main` and `v*` tags, reach `prod-i-application-certificate`.

## Testing

`cargo test` runs the unit tests for all four modules and the E2E tests. `client.rs` and `signer.rs` tests mock the service with `wiremock`. `signer.rs` also asserts byte-identical output between remote signing and local signing with the same key, using `tests/fixtures/`.

`cargo test --test e2e` runs only the E2E tests. Error cases (missing token, non-HTTPS URL, cert type mismatch, `401`, unknown flag) run on any OS. Signing tests need macOS with the Xcode command line tools (`cc`, `codesign`, `hdiutil`, `pkgbuild`, `pkgutil`) and are compiled out elsewhere. They check the signature state of the generated inputs, sign each artifact type (Mach-O and `.app` both ad-hoc signed and unsigned), verify the signature and its certificate (`codesign`, or `apple-xar` for `.pkg`, since `pkgutil` doesn't tell an invalid signature from an untrusted certificate), and compare the CodeDirectory against local signing with the same key.

Before committing: `cargo fmt --check` and `cargo clippy --all-targets -- -Dwarnings`. After a `Cargo.lock` change, also `scripts/gen-copying.sh`.

## CI

Workflows reference actions by tag. `.github/workflows/actions.lock` (generated by `gh actions-lock`) records the commit each tag resolves to, including transitive dependencies, and GitHub Actions runs those commits. After editing any workflow's `uses:`, regenerate it with `gh actions-lock` and commit both. `.github/workflows/verify-lockfile.yml` runs `gh actions-lock --verify` on pull requests and pushes to `main`, and fails if the lockfile is stale. Dependabot's `github-actions` updates regenerate the matching lockfile entries in the same PR, with no extra config.

`.gitlab-ci.yml` runs `fmt`, `shellcheck`, `copying` (`scripts/gen-copying.sh --check`) (on every `.sh` file under `scripts/`), `clippy` and `test-linux` on Linux. `test-macos` (full E2E) and `build-macos` (release binaries for both targets, plus a universal one made with `lipo`, unsigned) run on a macOS runner. `sign-macos` (trusted refs only) and `sign-macos-staging` (other branches) also run on a macOS runner, without the toolchain, from the shared `.sign-macos-service` job. macOS runners are scarcer than Linux ones, so these jobs run less often. They always run on the default branch and on tags. On other branches, they run only when the code, tests, scripts, toolchain or CI config differ from `main`. All build and test jobs install the toolchain pinned in `rust-toolchain.toml`, whatever the runner image ships. `sign-macos`, `notarize`, `verify-macos`, `package` and `release-s3` run after `build-macos`, in that order; see "Releases" above for what each does and which refs they run on.

`check-release-tag` (GitLab) only exists on a `v*` tag; the `check-tag` job (GitHub, `.github/workflows/release.yml`) always runs, but its `scripts/check-release-tag.sh` step only runs on a tag. Either way, a mismatched tag fails the check, which blocks building, packaging and publishing. See "Releases" above for exactly how each CI system gates its build, packaging and publishing on that check, and for how `.github/workflows/release.yml` also runs on `main`.
